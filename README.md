# NCDC 採用課題 フロントエンド

[recruit-frontend](https://github.com/ncdcdev/recruit-frontend)（バックエンド課題リポジトリ）に対する、フロントエンド実装です。サイドバーでページの一覧表示・作成・削除を行い、メインエリアでページのタイトルと本文を編集できます。

## セットアップ

**Node.js 22.12 以上**が必要です（Vitest 5 と、バックエンドの要件）。

### 1. バックエンドを起動する

```bash
git clone https://github.com/ncdcdev/recruit-frontend.git
cd recruit-frontend
npm install
cp ./data/bk-dev.sqlite ./data/dev.sqlite
npm run migration:run
npm run start
```

`http://localhost:3000` で API が起動します（`http://localhost:3000/api` に Swagger あり）。

### 2. フロントエンドを起動する

パッケージマネージャーは **pnpm** です。`corepack enable` を実行すれば別途インストールは不要です。

```bash
corepack enable        # pnpm が未導入の場合のみ
pnpm install
cp .env.example .env   # バックエンドの URL が異なる場合は VITE_API_BASE_URL を変更
pnpm run dev
```

`http://localhost:5173` で確認できます。

## 技術選定

| 技術 | 用途 | 選定理由 |
| --- | --- | --- |
| React 19 + TypeScript + Vite | 基盤 | 課題は画面が1つの SPA で、SSR・SEO もサーバー側の処理も不要（バックエンドは既存）なため、Next.js などのフレームワークは使わず React + Vite で構成した。React は TanStack Query や Testing Library など周辺ライブラリが最も充実している。Create React App は非推奨のため Vite を使用 |
| Tailwind CSS v4 | スタイリング | デザイン仕様の色・文字サイズを `@theme` にトークンとして集約できる。スタイルがマークアップと同じファイルに書かれるため、人も AI エージェントも 1 ファイルで構造と見た目を把握でき、CSS ファイルとの食い違いが起きにくい |
| TanStack Query | サーバー状態 | 取得・キャッシュ・更新後の再取得を `useEffect` で手書きせずに済む |
| zod | API レスポンスの検証 | TypeScript の型は実行時に消えるため、外部から来るデータを境界で検証する |
| Vitest + Testing Library + MSW | テスト | Vite の設定をそのまま共有できる。MSW はネットワーク層で差し替えるので、本番と同じ `fetch` のコードをテストできる |
| sonner | トースト通知 | 削除・作成の結果と API エラーを画面を塞がずに伝えるため。追加の状態を持たずに済み、作成直後の「取り消す」のようなアクション付き通知も出せる |
| oxlint | Lint | 設定がほぼ不要で高速 |
| pnpm | パッケージ管理 | npm より高速でディスク効率が良い。`package.json` に宣言していないパッケージを import できないため、宣言漏れの依存に気づける |

Zustand などの状態管理ライブラリは**意図的に採用していません**。サーバー由来のデータは TanStack Query、それ以外（選択中のページ、編集中かどうか）はコンポーネントの `useState` で足りる規模のためです。

ルーティングライブラリも使っていません。画面が1つだけで、URL で切り替える対象が無いためです（TanStack Router を一度導入しましたが、使っている機能が無かったため削除しました）。

## 設計方針

### ディレクトリ構成

`components/` `hooks/` のような種類別ではなく、`src/features/sidebar/` `src/features/page-editor/` のように**機能単位**で分けています。1 つの機能に関するコードが 1 か所にまとまり、変更の影響範囲を追いやすいためです。

```
src/
├── api/              バックエンドの各エンドポイントに対応する薄いラッパー（fetch + zod）
├── features/
│   ├── pages/        ページ一覧のサーバー状態（TanStack Query の取得・更新・作成・削除）
│   ├── sidebar/      ページ一覧・選択・一覧編集モード
│   └── page-editor/  タイトル・本文の表示と編集（編集状態と保存は useEditSection に集約）
├── components/ui/    複数の機能から使う汎用部品（Button）
├── lib/              QueryClient（エラー通知の集約）
└── App.tsx           画面全体のレイアウトと、選択中のページなどの状態
```

### `Page` と `Content`

バックエンドのエンティティ名は `Content` ですが、UI 側のコードでは画面上の概念どおり `Page` と呼び、`Content` という名前は `src/api/` の中だけに閉じ込めています。バックエンドの命名が UI のコードに広がらないようにするためです（用語の定義は [CONTEXT.md](./CONTEXT.md)）。

### 同型のセクションの扱い

タイトルと本文は「Edit → 編集 → Cancel/Save」という同じ振る舞いを持ち、違うのは表示だけ（1行入力か、複数行入力＋文字数カウンタか）です。そのため振る舞いは `useEditSection`、ボタンは `EditActions` に寄せ、各セクションには表示の違いだけを残しています。

文字数の判定と保存する値をそろえる処理もこの hook の中にあります。ここを2か所に書き分けると、前後に空白を付けるだけで上限を超えた値が保存できてしまい、しかも片方だけ直して気づけません。

### API データ層

`src/api/pageApi.ts` をバックエンドとの境界とし、レスポンスを zod で検証したうえで、バックエンド固有の挙動をここで吸収しています。

- `title` / `body` は DB 上 `null` になりうる（新規作成直後など）ので、空文字にそろえる
- 存在しない ID を更新すると、バックエンドは 400 ではなく `200 + null` を返すため、検証でエラーとして扱う
- `fetch` は 4xx/5xx でも例外を投げないので、ステータスを見て明示的にエラーにする
- `POST /content` はボディを省くとバックエンドが 500 を返すため、空オブジェクトを送る

### デザインの再現

寸法はスクリーンショットの目視ではなく `Design/DesignSpec/index.html` に埋め込まれた Sketch のレイヤー情報から取り、色・文字サイズは `src/index.css` の `@theme` にトークンとして集約しています。

### テスト

不具合が起きやすいバックエンドとの境界（`src/api/pageApi.ts`）を重点的にテストしています。MSW で応答を差し替え、`null` の正規化・エラーステータス・`200 + null` などを検証しています。あわせて汎用部品の `Button` と、編集状態を扱う `useEditSection`（バリデーションの判定と保存値がずれないこと、保存失敗時に入力を失わないこと）もテストしています。

見た目だけのコンポーネントにはテストを置いていません。デザインへの追従で頻繁に変わる部分をテストで固定すると、実際の不具合を捕まえないまま修正コストだけが増えるためです。

## 要件との対応

| 要件 | 実装 |
| --- | --- |
| サイドバーに全ページを表示 | `src/features/sidebar/Sidebar.tsx` |
| サイドバーでページを作成（「+」ボタン） | 一覧編集モードの「New page」ボタン |
| 「-」ボタンでページを削除 | 一覧編集モードで各行に出る削除アイコン |
| タイトル・本文をそれぞれ編集・保存 | `src/features/page-editor/` |
| バリデーション（タイトル 1〜50 文字、本文 10〜2000 文字） | 範囲外の間は Save ボタンを無効化（`src/features/page-editor/useEditSection.ts`） |
| テストコード 1 つ以上 | 上記「テスト」参照 |

「+」「-」ボタンは、デザイン仕様ではそれぞれ「New page」ボタンと削除アイコンとして描かれているため、デザイン仕様に合わせています。

## 追加実装（仕様に明記されていない機能）

- **削除前の確認ダイアログ**: バックエンドに復元 API が無く、取り消しができない操作のため。削除後は「ページを削除しました」とトーストで通知します
- **新規作成の取り消し**: 作成後のトーストの「取り消す」で、作成したページを削除できます（確認ダイアログを挟まずにすぐ作成できるようにするため）
- **API エラーのトースト通知**: 取得・保存・作成・削除の失敗を `src/lib/queryClient.ts` で一括して通知します。利用者には HTTP の詳細は意味がないため、文言は「処理に失敗しました。時間をおいて再度お試しください」に統一しています。保存に失敗した場合は入力内容を残したまま編集状態に留まります
- **文字数の数え方をそろえる**: 文字数は `trim()` してから数え、**保存する値も同じ trim 後の値**にしています。バックエンドは長さを検証しないため、フロントが守らないと制約が実質無効になります（数える値と保存する値が違うと、前後に空白を付けるだけで 51 文字以上のタイトルが保存できてしまいます）
- **本文の文字数カウンタ**: 入力欄の下に現在の文字数と制限を表示
- **ページ未選択時の空状態**: 初期表示と、選択中のページを削除した直後に「ページを選択してください」を表示
- **無題ページの表示**: タイトルが空のページ（新規作成直後）はサイドバーに「無題」とグレー・斜体で表示
- **新規作成したページを自動で選択**: 作成後すぐに編集を始められるようにするため
- **入力欄の読み上げ対応**: デザイン上、入力欄はタイトル・本文の表示と入れ替わる形で見えるラベルがないため、`aria-label` で名前を付けています。本文の入力欄は文字数カウンタと `aria-describedby` で結び、制限が読み上げられるようにしています
- **レスポンシブ対応**: 768px 未満では 2 カラムをやめ、モバイルアプリと同じ単ペインにします（未選択＝一覧が全画面、選択中＝編集エリアが全画面 +「← 一覧へ」で戻る）。768px 以上の寸法はデザイン仕様どおりで変えていません
